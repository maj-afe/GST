## SECTION 13: INSTALLATION, DEPLOYMENT & AUTO-UPDATER STRATEGY

*Pharmacies do not have IT departments. Installation must be a "Next -> Next -> Finish" experience. The application must install itself, configure itself, and update itself silently.*

### 13.1 The Installer (Tauri Bundler)
*   **Output Format:** A single `.msi` (Windows Installer) or `.exe` (NSIS) file.
*   **Bundled Dependencies:** The installer must bundle:
    *   The React frontend (compiled HTML/JS/CSS).
    *   The Rust backend (compiled binary).
    *   A local SQLite database engine (or PostgreSQL if multi-PC).
    *   **WebView2 Runtime:** Tauri requires WebView2. The installer must check if it exists and install it silently if it doesn't. (This is standard for modern Windows apps).
*   **Install Location:** `C:\Program Files\PharmaLocal` (Requires Admin privileges for the first install).

### 13.2 First-Run Experience (The Setup Wizard)
When the app is launched for the first time, it must not show the dashboard. It must show a 5-step wizard:
1.  **Store Details:** Input Pharmacy Name, Address, GSTIN, Drug License Number, Phone. (This auto-populates invoice headers).
2.  **Admin User Creation:** Create the first user (Owner/Admin). Set a strong password. This password encrypts the local database.
3.  **Hardware Setup:**
    *   *Printer:* Dropdown to select the thermal printer (e.g., "TVS RP 3160"). Button to "Print Test Bill".
    *   *Scanner:* Instructions to plug in the USB scanner. A test input box to scan a barcode and verify it registers.
4.  **GST & Compliance Setup:** Select default tax rates (e.g., 5%, 12%, 18% for different drug categories). Input GST API credentials (if using e-invoicing).
5.  **Data Import (Migration):** If the user is migrating from an old software (like Pharma 2007), provide a CSV/Excel template to import their existing `items`, `customers`, and `batches`.

### 13.3 The Auto-Updater (Tauri Updater Plugin)
*   **The Problem:** You release a bug fix. You can't drive to 500 pharmacies to update their software.
*   **The Solution:**
    *   Host a `latest.json` file on a remote server (e.g., GitHub Releases, AWS S3, or your own VPS).
    *   The JSON contains the version number, release notes, and the signed download URL.
    *   The Rust backend checks this JSON every time the app starts (or every 24 hours).
    *   If a new version is found, it downloads the update in the background.
    *   A small toast appears: *"Update ready. Restart to apply."*
    *   **Security:** The update package **must be code-signed**. The Rust backend verifies the signature before installing to prevent man-in-the-middle attacks.
*   **Offline Handling:** If the pharmacy has no internet, the update check fails silently. The app continues to work perfectly on the old version.

## SECTION 14: TESTING & QUALITY ASSURANCE (QA) STRATEGY

*Vibe coding without testing creates a house of cards. You must enforce a testing culture.*

### 14.1 Unit Testing
*   **Frontend (React):** Use `Vitest` and `React Testing Library`.
    *   Test the `useCartStore` (Zustand): Ensure adding an item, applying a discount, and calculating GST works mathematically.
    *   Test the `useDatabase` hook: Mock the Tauri `invoke` function to ensure the UI handles database responses correctly.
*   **Backend (Rust):** Use `cargo test`.
    *   Test the tax calculation engine (CGST/SGST/IGST).
    *   Test the FEFO (First Expiry First Out) batch selection algorithm.
    *   Test the SQL queries against an in-memory SQLite database.

### 14.2 Integration Testing
*   Use `Playwright` to automate the UI.
*   **Test Scenario:** Open app -> Search item -> Add to cart -> Apply discount -> Checkout -> Print. Verify the database was updated.
*   **Hardware Mocking:** Create a "Virtual Printer" class in Rust that writes ESC/POS commands to a text file instead of a physical port. This allows you to test invoice layouts without wasting paper.

### 14.3 Offline Mode Simulation (The "Airplane Mode" Test)
*   This is the most critical test for this specific architecture.
*   **How to test:**
    1.  Disconnect the internet.
    2.  Generate 10 invoices.
    3.  Attempt to send WhatsApp messages and e-invoices.
    4.  Verify the UI does *not* freeze or crash.
    5.  Verify the `sync_outbox` table has 10 pending `SEND_WHATSAPP` and 10 pending `GENERATE_E_INVOICE` records.
    6.  Reconnect the internet.
    7.  Verify the background worker processes the queue and updates the status to `SUCCESS`.
*   **Tools:** Use `Clumsy` (Windows) or `Network Link Conditioner` to simulate packet loss and high latency.
